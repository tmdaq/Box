# HLS 预缓存通过本地分片代理实现，只做透明字节缓存

点播 HLS 的预缓存不使用各播放器内核自带的缓存（Exo 的 `CacheDataSource`、IJK 的 `ijkio:cache`、阿里播放器的配置），而是在本地服务 `RemoteServer` 上加一个分片代理：把 m3u8 里的分片地址改写到代理上，由代理按预缓存窗口多线程下载分片到磁盘。这样做的原因是项目同时支持 Exo、IJK、阿里和系统播放器 4 个内核，只有代理能对它们一视同仁；而且内核自带的缓存都是被动的，不会主动往后预取。

代理只做透明的字节缓存，不解密。分片原样下载、原样存储、原样返回；`#EXT-X-KEY` 只把 URI 补成绝对地址，由播放器自己去源站拿密钥并解密。改写 m3u8 时，除了分片地址那一行，其余内容一律不动，`EXT-X-MEDIA-SEQUENCE` 和分片的个数、顺序都保持不变，因为没写 IV 时 AES-128 用分片序号当 IV。

## Considered Options

- **调大各内核的内存缓冲**：改动最小，但只能在内存里缓冲几十秒到一两分钟，而且要按内核分别调；作为补充手段保留，不作为本方案。
- **代理解密后返回明文**：可以顺便处理一些播放器不支持的加密方式，但代理要管理密钥，磁盘上会留下明文，CPU 开销也更大，所以否决。
- **出错时整段回退到原地址重新播放**：会打断播放、丢失进度。改为按分片透明处理：源站返回什么错误，就原样返回给播放器；代理自身出错（比如磁盘写入失败）时，本次会话降级为纯转发。这样播放器看到的效果和直连源站一样，现有的「切内核重试」逻辑也继续生效。

## Consequences

- 外部播放器（MX、Reex、Kodi）不使用预缓存，因为 App 退到后台后预缓存会话的生命周期管不住。
- 控制栏显示的网速变成播放器从本地读数据的速度，不再反映源站速度。
- 分片代理只接受 `127.0.0.1` 的请求，避免局域网里的其他设备借它下载或读取缓存。
